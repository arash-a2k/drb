# Project Guide for AI Agents

This repository is a static Expo Router web project for a dentist landing site. It uses React DOM elements, Tailwind CSS classes, and JSON files for translated content. Expo is mainly used for routing and static export.

## Main Stack

- Runtime/router: Expo Router (`expo-router/entry` in `package.json`).
- UI: React components that render regular web HTML elements (`div`, `section`, `img`, `a`, etc.).
- Styling: Tailwind CSS from `global.css` and `tailwind.config.js`.
- Deployment: static web export to `dist`, then `gh-pages`; see `Readme.md` for deployment details.

## Directory Roles

- `app/`: URL routes only. Expo Router turns files here into pages.
- `pages/`: page-level content components and their colocated translation JSON.
- `components/`: reusable sections, layout components, page templates, and component-level translation JSON.
- `hooks/`: shared React hooks and providers. Currently this is mainly language context.
- `utils/`: browser helpers for language detection, query params, and truthy parsing.
- `assets/`: source assets used locally.
- `public/`: static files for exported site. The deploy prep copies `assets/*` into `public/assets/`.
- `translations/`: shared translation JSON used by multiple components.

## Routing Model

The site uses language-prefixed routes as canonical pages:

- `/fa`
- `/en`
- `/ru`
- `/fa/contact-us`
- `/en/contact-us`
- `/ru/contact-us`

Root non-language paths redirect to the default Persian route:

- `app/index.js` redirects `/` to `/fa`.
- `app/about-us.js` redirects `/about-us` to `/fa/about-us`.
- `app/contact-us.js` redirects `/contact-us` to `/fa/contact-us`.

The dynamic language route lives under `app/[lang]/`. Static language pages are generated by `generateStaticParams()` in `app/[lang]/_layout.jsx`. If adding a new supported language, update this file and the accepted language lists in `hooks/index.js` and `utils/index.js`.

## Layout

`app/_layout.js` wraps every page with:

- `HelmetProvider`
- `LanguageProvider`
- global `Header`
- route `<Slot />`
- global `Footer`

`app/+html.jsx` controls the static HTML shell. Keep it simple: it is not the place for runtime React logic.

## Language and Translations

Language is provided by `LanguageProvider` in `hooks/index.js`.

- Supported languages are currently `fa`, `en`, and `ru`.
- Initial language is detected from the hostname/path by `getLanguageFromUrl()` in `utils/index.js`.
- Path language wins over subdomain language.
- If no URL language is found, it falls back to `localStorage.lang`, then `fa`.
- Components read language with `const { lang } = useLanguage()`.
- Most components fall back to English with `text[lang] || text['en']`.

Translation JSON is usually colocated with the component that owns the content:

- Page content: `pages/home/home.json`, `pages/about/about.json`, `pages/contact/contact.json`.
- Component content: `components/header/header.json`, `components/footer/footer.json`, `components/treatments/treatments.json`.
- Shared content: `translations/contact.json`, `translations/drb.json`.
- Treatment route content is currently inside `app/[lang]/treatments/.../*.json`.

Keep the same object shape for every language key. If a page supports `fa`, `en`, and `ru`, every key consumed by the component should exist under each language or have an intentional fallback.

For Persian pages, set direction with:

```jsx
const dir = lang === 'fa' ? 'rtl' : 'ltr';
return <div dir={dir}>...</div>;
```

## Automated Page Creation

When an agent is asked to create a page from provided text and images, it should treat the task as a content-to-page assembly workflow. The agent should choose the best page type, place content in translated JSON, create the route wrappers, and update navigation when needed.

### Page Type Categories

Choose the simplest page type that fits the supplied content.

- `single-column`: Best for text-heavy informational pages, FAQs, policies, or pages with no strong primary image. Layout is one centered content column with headings and sections.
- `two-column`: Best for a landing or service page with one primary image and concise explanatory text. One side is image, the other side is title/content. This can reuse `ArticleSolo` when the shape fits.
- `hero-with-sections`: Best when there is a strong hero image plus multiple body sections. Use this for major treatment/service pages where the first image should lead the page.
- `content-with-image-grid`: Best when text is paired with many treatment/gallery images. Prefer existing `components/pageTemplates/ContentWithImageGrid.jsx`.
- `solo-image-content-lines`: Best when the page needs one hero image, multiple content sections, and a gallery/image grid. Prefer existing `components/pageTemplates/SoloImageContentImageLines.jsx`.
- `gallery-only`: Best for before/after images or treatment examples with minimal text. Reuse `ImageGrid`.
- `contact/location`: Only for location, map, hours, and phone pages. Reuse or extend `pages/contact/Contact.jsx` instead of creating another contact implementation.

If the page is a dental service or treatment, prefer `content-with-image-grid` or `solo-image-content-lines`. If the page is about the clinic, doctor, process, or trust-building content, prefer `two-column` or `single-column`.

### Content Input Mapping

Before editing files, classify the input:

- Page slug: URL-safe lowercase slug, for example `teeth-whitening`.
- Page title: one title per language if provided.
- Intro/summary: short paragraph for the top of the page.
- Sections: ordered headings and body text.
- Images: identify one hero image if available, then remaining gallery images.
- Image alt text: create descriptive alt text for every image in every language when possible.
- Navigation placement: decide whether this belongs in the main header, the treatments dropdown, or no navigation.

Do not hardcode user-visible page text in JSX unless it is not translated content. Put translated page copy in JSON.

### Translation Workflow

Create one translation JSON file for the page. Use the same shape for each supported language:

```json
{
  "fa": {
    "title": "",
    "intro": "",
    "heroImage": "/assets/images/example/hero.webp",
    "sections": [
      {
        "id": "overview",
        "title": "",
        "content": "",
        "bold": []
      }
    ],
    "images": [
      {
        "src": "/assets/images/example/image-1.webp",
        "alt": ""
      }
    ]
  },
  "en": {
    "title": "",
    "intro": "",
    "heroImage": "/assets/images/example/hero.webp",
    "sections": [],
    "images": []
  },
  "ru": {
    "title": "",
    "intro": "",
    "heroImage": "/assets/images/example/hero.webp",
    "sections": [],
    "images": []
  }
}
```

If the user supplies text in only one language, do not invent medical/dental translations unless explicitly asked. Use the supplied language as source and either:

- leave missing languages as a clear fallback copy if the existing project pattern accepts that, or
- populate `en` fallback and keep other missing languages structurally complete with empty arrays/strings.

The preferred project behavior is `text[lang] || text.en`. If a language key exists but is incomplete, the fallback will not apply automatically, so keep each language object complete.

### File Creation Checklist

For a normal page:

1. Create `pages/<page-slug>/<PageName>.jsx`.
2. Create `pages/<page-slug>/<page-slug>.json`.
3. Add `app/[lang]/<page-slug>.jsx` that imports and renders the page component.
4. Add `app/<page-slug>.js` that redirects to `/fa/<page-slug>`.
5. Update navigation if the page should be discoverable.
6. Use `/assets/...` paths for images.
7. Confirm the page renders for `/fa/<page-slug>`, `/en/<page-slug>`, and `/ru/<page-slug>`.

For a treatment page:

1. Create `app/[lang]/treatments/<page-slug>/index.jsx`.
2. Create `app/[lang]/treatments/<page-slug>/<page-slug>.json`.
3. Use a page template from `components/pageTemplates/`.
4. Add the treatment to `components/header/header.json` dropdown items for every language that exists in the navbar JSON.
5. Add a redirect route only if a non-language URL is needed, for example `app/treatments/<page-slug>/index.js` redirecting to `/fa/treatments/<page-slug>`.

### Component Template Pattern

Use a page component like this for page-level content under `pages/`:

Example route wrappers:

```jsx
// app/[lang]/new-page.jsx
import React from 'react';
import NewPage from '../../pages/new-page/NewPage';

export default function IndexPage() {
  return <NewPage />;
}
```

```jsx
// app/new-page.js
import React from 'react';
import { Redirect } from 'expo-router';

export default function IndexPage() {
  return <Redirect href="/fa/new-page" />;
}
```

Example translated page component:

```jsx
import React from 'react';
import { useLanguage } from '../../hooks';
import * as text from './new-page.json';

export default function NewPage() {
  const { lang } = useLanguage() || { lang: 'fa' };
  const content = text[lang] || text.en;
  const dir = lang === 'fa' ? 'rtl' : 'ltr';

  return (
    <main dir={dir} className="bg-gray-50">
      <section className="container mx-auto px-4 py-10">
        <h1 className="text-4xl font-bold text-center">{content.title}</h1>
      </section>
    </main>
  );
}
```

For a template-backed treatment page, keep the route component thin:

```jsx
import React from 'react';
import { useLanguage } from '../../../../hooks';
import ContentWithImageGrid from '../../../../components/pageTemplates/ContentWithImageGrid';
import * as text from './teeth-whitening.json';

export default function TeethWhitening() {
  const { lang } = useLanguage() || { lang: 'fa' };
  const content = text[lang] || text.en;
  const dir = lang === 'fa' ? 'rtl' : 'ltr';

  return (
    <div dir={dir}>
      <ContentWithImageGrid
        images={content.images}
        title={content.title}
        sections={content.sections}
      />
    </div>
  );
}
```

### Navigation Updates

Header text lives in `components/header/header.json`; header rendering lives in `components/header/Header.jsx`.

- For a main navigation item, add translated labels to `header.json` and add a link in `Header.jsx`.
- For a treatment dropdown item, add an item to `navbar.<lang>.dropdown.items`.
- Links in dropdown items should be relative to the language prefix, for example `treatments/teeth-whitening`; `Header.jsx` renders them as `/${lang}/${item.link}`.
- Keep navigation labels short because the header is already dense on mobile.

### Validation Checklist

After creating a page, check:

- The route file exists under `app/[lang]/...`.
- The default redirect exists when the page has a non-language URL.
- The JSON has `fa`, `en`, and `ru` keys or the component intentionally falls back to `en`.
- No translated text is hardcoded in JSX.
- Every image path starts with `/assets/`.
- Every image object used by `ImageGrid` has `src` and `alt`.
- Persian pages use `dir="rtl"` and other languages use `dir="ltr"`.
- Tailwind classes are inside `pages/` or `components/`, or `tailwind.config.js` includes the file path.

## Adding a Treatment Page

Treatment pages currently live under `app/[lang]/treatments/<slug>/`.

Typical options:

- Use `components/pageTemplates/ContentWithImageGrid.jsx` for content plus image grid.
- Use `components/pageTemplates/SoloImageContentImageLines.jsx` for a hero image, content sections, and image grid.

For a new treatment:

1. Add `app/[lang]/treatments/<slug>/index.jsx`.
2. Add a JSON file next to it, following the shape of an existing treatment JSON.
3. Import the relevant page template.
4. Add a dropdown item in `components/header/header.json` for every displayed language.

Use asset paths like `/assets/images/...` in JSON and JSX. These work locally through Expo and after deployment because `pre-export` copies `assets/*` to `public/assets/`.

## Hooks and Utilities

`hooks/index.js` exports:

- `LanguageProvider`
- `useLanguage`

`utils/index.js` exports:

- `getLanguageFromUrl()`
- `getQueryParam(key)`
- `isTruthy(value)`

Do not add page-specific logic to these files. Keep them for shared behavior used by multiple pages/components.

## Tailwind Notes

Tailwind scans `pages/`, `components/`, and root JS/TS files in `tailwind.config.js`. It does not currently scan `app/**/*`.

Practical rule: put styled UI in `pages/` or `components/`, and keep `app/` route files thin. If adding substantial Tailwind markup directly inside `app/`, update `tailwind.config.js` content paths to include `./app/**/*.{js,tsx,ts,jsx}`.

Avoid adding `node_modules` or overly broad paths to Tailwind content. That can make local runs and exports very slow.

## Assets and Static Files

Use `/assets/...` in `img src` paths.

During deploy prep, `npm run pre-export`:

- clears `public/assets/*`
- creates `public/.nojekyll`
- copies `assets/*` into `public/assets/`

Keep `CNAME` and the Google verification HTML file in place; they are part of the deployed GitHub Pages setup.

## Commands

- Start local web development: `npm run web`
- Prepare assets for export: `npm run pre-export`
- Export static web build: `npm run pre-deploy`
- Deploy exported `dist`: `npm run deploy`

## Development Conventions

- Keep route files in `app/` small; put real page UI in `pages/` or reusable `components/`.
- Reuse existing page templates before creating a new layout pattern.
- Keep JSON content separate from JSX when text is translated.
- Prefer existing shared contact/header/footer translation files over duplicating clinic details.
- Add images with meaningful `alt` text where the component supports it.
- Preserve default Persian redirects for non-language URLs.
- After adding or changing translated pages, check all supported language URLs.
